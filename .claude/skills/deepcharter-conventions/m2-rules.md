# Rules for M2 work

- **Pod state is an attachment, never a `PodData` field.** `PodData`, `PodEntity`, `PodMovement` and `PodTuning` take no more changes, except #60's, the landing rule of #319 and its retuned `hullDamagePerSpeed` of #1432 ([ADR 0035](../../../docs/adr/0035-pod-landing-damage-reads-impact-speed.md)) and `PodEntity`'s interpolation override of #961 ([ADR 0074](../../../docs/adr/0074-pods-stay-server-authoritative-and-the-client-slides-them-over-two-ticks.md)), which #1041 changed to return `PodGlide` ([ADR 0082](../../../docs/adr/0082-the-client-coasts-a-pod-through-a-late-server-and-caps-its-catch-up.md)), and #1281's transient turn-rate and quarter-turn fields on `PodEntity` with the steering in `PodMovement` ([ADR 0095](../../../docs/adr/0095-pods-steer-like-a-boat-and-the-pilots-camera-chases-them.md)). `PodTuning.Movement` values (not fields) may be retuned by a PR that names the readers it checked (#1276). The pattern is `attachment/Versioned` with the throwaway example in `src/gametest/.../test/support/TestAttachments`: an immutable record with no version field, a body `MapCodec`, and an `AttachmentType<Versioned<T>>` registered from your feature's own `XRegistry` with `persistent(Versioned.codec(VERSION, BODY))`, `initializer(() -> Versioned.of(DEFAULT))` and, if a client reads it, `syncWith(Versioned.streamCodec(VERSION, STREAM), AttachmentSyncPredicate.all())` (or `targetOnly()`). Read it with `Versioned.readable(pod, T)` (see the Unreadable rule below) and change it with `Versioned.modifyOrThrow(pod, T, v -> ...)`. It crosses a breach by itself: the arriving pod is a new entity that vanilla fills from the old pod's saved data, which includes persistent attachments. `copyOnDeath` is for players and is not used. The crossing test guards this.
- New pod tunables that only affect how the client draws a pod go in `PodGlideTuning`, not `PodTuning`.
- **Every SavedData and attachment has a version, and never fails to decode.** Versions start at 1. Fabric loads all of an entity's attachments as one map and silently drops the whole map if it fails to decode, so a bad entry would reset every feature's attachments and be overwritten on the next save. `Versioned.codec` therefore decodes an unknown or missing version (or a body that does not parse) to `Versioned.Unreadable`, which keeps the raw data and writes it back unchanged. `Versioned.orThrow`, `Versioned.modifyOrThrow` and `SavedState.orThrow` throw on `Unreadable`, naming the owner, the attachment and the version. On the wire an unreadable value is a marker; a client given a different version than it reads throws, which disconnects it. To change a shape, bump the version and make the decode read the old one. A `SavedData` follows the same rule: keep a `version` field, keep data of another version rather than dropping it, and fail loud on use.
- **A wire `StreamCodec` decode refuses a value its encoder cannot produce (it throws), rather than clamping. Clamping belongs to the disk codec.** A throw disconnects the client, as a version mismatch does.
- **A reload-listener table that the client needs must be synced, or the client must decide from the synced tag only.** See `PodFuelItems`.
- **A change to a persisted format (pod save, SavedData, attachment) carries a version, with an `Unreadable` fallback for unknown versions, plus a GameTest that loads the previous format and asserts the outcome (migrate, or fail loud).** A decode that skips entries silently is a drop.
- **A feature that records progress from a player's position or depth skips spectator and creative players and names the dimensions it counts** (`DeepestPoint`: the surface and the layers, not the Nether or the End).
- **A feature that acts on a pod's cargo or parts asks `PodComponents.mayAccess(pod, charter)`; never reimplement the ownership rule.**
- **A feature that moves a pod carrying players or cargo somewhere its owner didn't choose (tow, push, teleport) names its ownership rule in its ADR.**
- Code on a tick, join, sync or gameplay-callback path never throws on `Unreadable` data. Read versioned attachments with `Versioned.readable`; hold a SavedData's state in a `SavedState` and check `isReadable()` (both log once and never throw). `orThrow` and `modifyOrThrow` are for explicit calls and commands only. The throwing charter forms (`Charters.charterOfOrThrow`, `findOrThrow`, `allOrThrow`) are for commands and explicit actions; use `Charters.readableCharterOf` and `readableFind` on tick, join, sync or callback paths. `allOrThrow` has no readable form: it is for commands and guarded terminal views only. Test a feature with `UnreadableChecks`.
- A server-tick callback that touches several outposts, charters or pods catches and logs per item, so one bad record never aborts the rest or crashes the tick.
- **To rename or remove one of our pod entity types, add its old id to `PodRenames` (one line, never deleted); otherwise vanilla drops every saved pod of that type with its cargo on chunk load** ([ADR 0045](../../../docs/adr/0045-a-renamed-pod-entity-type-is-read-through-a-table-in-entity-type-by.md)).
- **Pods change through `PodEvents`, not through edits to the pod.** `HULL_DEPLETED` (hull reached 0), `CAN_MOUNT` (veto boarding), `IS_POWERED` (cut power: no movement, no drill, no fuel burn), `EXTRA_MASS` (cuts lift like cargo; a negative or NaN total throws), `IGNORES_BLOCK_COLLISION` (pass through blocks) and `AFTER_TICK` (server tick end; a read-only listener registers in `PodEvents.OBSERVE`, which runs before the default phase where towing moves the pod). Everything is server-side. Predicates are ANDed (one no vetoes), except `IGNORES_BLOCK_COLLISION`, where one yes is enough. Call the static helpers `PodEvents.canMount`, `isPowered`, `extraMass` and `ignoresBlockCollision`, never the invokers. With no listener, a pod behaves as in M1. Fabric events cannot be unregistered, so a test listener must act only on the pods that test marks. `PodStats.of(pod)` (#60) is the seam for stats.
- **Call the stubs without waiting.** `Directives.fire(ServerPlayer, Identifier)` (`handbook/`, filled by #61) completes a handbook directive for the player's charter. `Transmissions.fire(CharterId, Identifier)` (`transmission/`, filled by #62) fires a transmission once for a charter. Both do nothing until their issue lands, and their signatures are frozen. `charter/CharterId` is a record around a random UUID made when a charter is founded, never reused and never a player's UUID, with a `CODEC` and a `STREAM_CODEC`. #52 builds the charter around it.
- **A mapping the code calls permanent (ids, numbers, block-state encodings) is pinned by a test with literal expected values, not only by a test that the keys exist.**
- **Anything that carves a hollow in a layer, including a generated structure, seals its shell (fluids and gas pockets) before carving.** See `RoomSeal` and `StructurePlan.seal`.
- **Anything that places blocks in a chunk a player may still be sent (a structure drawn on `CHUNK_LOAD`, a pocket carved as a player crosses) calls `LightSync.holdSendUntilLit` after the last block.** Otherwise the client keeps the old light, because vanilla drops the light update of a chunk that is not ticking. Blocks placed in an already-sent, non-ticking chunk still lose their light packet.
- **A terminal action that spends does everything that can throw or refuse before the spend.**
- **A gate that holds a pod or player until a colony terminal acts applies only while that terminal can act (`Terminals.canServe`), or names its bootstrap fallback, with a GameTest of the offline case.** An offline terminal refuses every action (`EngineSoot.launchRefused`, #1280). On a tick path the gate treats every unreadable input the terminal depends on (its `RepairState`, `Charters`) as offline, and an `UnreadableChecks` test covers each.
- **Never gate gameplay or cleanup on an entity query:** it sees only loaded chunks, so "none found" can mean "not loaded". Decide from saved data (a SavedData, an attachment), and let a stale entity discard itself on `ServerEntityEvents.ENTITY_LOAD`. `checkEntityQueryGate` fails the build on a query in `src/main` or `src/client` without `// entity-query: <reason>` on its line or the one above; the reason says why the area is always loaded where the code runs, or why a miss is harmless.
- **A stamp or counter that retires entities by number is scoped to what it retires (one site, one position).** A global counter makes every caller's restore void every other's, and tests that share the world race on it (`ColonyDisplays` counts per pad centre and per hands position).
- **State held in memory to undo a change to player-owned persistent data (a respawn point, an inventory) is itself persisted, or the change is not made.**
- **Mixins** live in `<feature>/mixin/` and are registered in the config whose `package` is that folder: `deepcharter.mixins.json` for `surface.mixin`, `deepcharter.<feature>.mixins.json` otherwise (listed in `fabric.mod.json`). A client-only mixin lives in `client/<feature>/mixin/`, with its config named `deepcharter.<feature>.client.mixins.json` and the classes under the config's `client` array (`deepcharter.colony.client.mixins.json`). Mixin refuses to load any non-mixin class from a package a config owns, so one config never covers two folders or a parent package. They are used only where no Fabric event reaches; an ADR names the target method. A mixin that cancels `ServerPlayerGameMode.destroyBlock` calls `PlayerBlockBreakEvents.BEFORE` and `AFTER` itself, or its ADR names the listeners it skips. Test-only mixins in `deepcharter-test.mixins.json` are exempt from the ADR, but must fail loud on a rename (`defaultRequire: 1`), and either default to inert and reset in a `finally`, or be a deliberate always-on harness change stated in `tests.md`.
- **A background `ClientLevel` shares its renderer with the shown one:** every renderer-facing callback of `ClientLevel` and `ClientChunkCache` (`sendBlockUpdated`, `setBlocksDirty`, `setSectionDirtyWithNeighbors`, `setSectionRangeDirty`, `ClientChunkCache.onLightUpdate`) is cancelled when `SeamClient.isBackground(level)`.
- Every M2 issue's test classes and evidence scenario already exist as stubs ([tests.md](tests.md)). A new test class or scenario needs no registration. #53 creates `client/ui/` for the UI kit; it needs no init line.
- **A new attachment that gates gameplay on a tick path ships an `UnreadableChecks` test and states what the player gets when it is `Unreadable`; a safety net never silently switches off.**
- **A feature that places a mob itself, outside the vanilla spawner, honours the `spawn_mobs` game rule and Peaceful, and places only inside its own zone and the world bounds.** The rule gates the placing tick, not the helper a test calls (`Drifters.tick`; test worlds pin `spawn_mobs` false, so a test that drives the tick sets it and restores it).
- A client role derived from a synced list falls back to the visible passengers for a rider the list hasn't reached yet.
- **Screens:** a screen that hands control back to a container screen on a mouse press does it on the release instead, or the release reaches the container with the carried stack (`RecipeConsoleScreen`).

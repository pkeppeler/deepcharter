# Tests

Stubs marked `// Filled by #N` belong to that issue. Tests live in `src/gametest/.../test/`:

- Add test classes and evidence scenarios to the stubs that already exist. `gradle/gametest.gradle` generates the gametest `fabric.mod.json` entrypoint lists from the classes (an `@GameTest` method, `implements FabricClientGameTest`, or `extends EvidenceScenario`) and fails the build for a `*Test` or `*Scenario` class it cannot register; never edit a list. The lists are sorted by name, and no test may depend on that order. A test that swaps a world-global saved record (colony, hangar, repair state, serials) does it through `WorldData.with` or `WorldData.swap` (`test/support`), which set, run the body and restore in a `finally` on the same tick; a direct `getDataStorage().set(` in `src/gametest` fails the build. `WorldDataGuard` stops the server GameTest run if a swap lives into the next tick. `./gradlew runGameTest -PgametestOrder=reverse` runs the server suite in reverse name order to catch a leak. A server stub is `<Thing>Test`, a client stub `<Thing>ClientTest`, a scenario `evidence/<Thing>Scenario` named `m2-<thing>`. A scenario stub throws "stub: #N fills it" when it is selected, and does nothing in a plain run.
- A server GameTest writes a world clock (`setTotalTicks(`, `setPaused(`, `addTicks(`, `setRate(`) only through `TestClocks.paused` (`test/support`, restores in a `finally` on the same tick), or marks the line `// world-clock: <reason>`; the build fails otherwise, and client tests and evidence scenarios are exempt. The scan matches the method name, not the receiver: mark a non-clock `// world-clock: not a clock`. `tools/tests/world_clock_gate_check.py` tests this.
- A GameTest that cuts air into generated layer rock calls `RoomSeal.seal` first (generated lava and gas flood the cut otherwise).
- A new CHUNK_LOAD or other lifecycle listener needs a test that fires the real event or reloads a real chunk, not one that calls the handler directly.
- Run one client GameTest class with `./gradlew runClientGameTest -PclientTests=<filter>` or `tools/gametest.sh --client <filter>`. The filter is a comma-separated list of class names (simple or fully qualified) or globs (`Pod*ClientTest`; `*` matches any characters), matched against the client list that `generateGametestModJson` writes, and it also selects evidence scenarios. A term that matches no client class fails the build and names the term, so a typo never runs nothing and reports green. Without the property the list is the full one. The property is an input of the generation task, so changing it regenerates the list. A later plain `./gradlew build` or `runClientGameTest` regenerates the full list. `tools/tests/client_filter_gate_check.py` tests this, run by `tools/tests/gate_checks.py` (CI `build` job and pre-push hook).
- Run one GameTest, or a prefix of them, with `tools/gametest.sh '<test_id or prefix*>'` (quote the `*`). It runs `./gradlew runGameTest` from the repo root it lives in, sets the filter through `JAVA_TOOL_OPTIONS` (a bare `-D` on the Gradle command line is ignored), and fails when no test matches.
- `LavaBoreTest` (#231) is a measurement more than a regression test. By default it runs a 2-bore smoke case in seconds. `DEEPCHARTER_LAVA_BORES=<n> tools/gametest.sh 'lava_bore_test*'` runs <n> full bores of layer 1 (about 2.5 minutes for 100 on an 8-core M2) and prints `[lava-bore]` lines. `DEEPCHARTER_LAVA_BORES_LINING=<slabs>` makes the bot line (#313), and `DEEPCHARTER_LAVA_BORES_BRICKS=<n>` sets its starting bricks. `DEEPCHARTER_LAVA_BORES_LINER=<tier>` (#339) gives the pod a liner part of that tier instead and is measured alone: it is an error together with `_LINING`. `DEEPCHARTER_LAVA_BORES_PACK=<n>` puts that many bricks in a liner pilot's pack. The bot brakes in a fall; `DEEPCHARTER_LAVA_BORES_BRAKING=off` turns that off. `DEEPCHARTER_LAVA_BORES_SOUNDER=<tier>` (#373) gives the pod the real seep sounder part of that tier (1 or 2); the bot then reacts only to what the part tells it (its HUD state and range) and steps aside from the pocket it shows, and the part bleeds what the bot drills into; it is an error together with a `_GAS` other than `ignore`. `DEEPCHARTER_LAVA_BORES_GAS=avoid` (#368) makes the bot step aside from a gas pocket that a tier 3 scanner (`ScannerTuning.gasTier`) would show in its next slab; `ignore`, the default, bores straight through; `sounder1` and `sounder` are design bounds, not counterplay the game has (the bot knows every pocket of its footprint in the 2 slabs below; `sounder` also knows the step's cells and tries all four sides). The cause tally is priority-ordered: lava, then gas, then landing, then crust. The numbers are in [mechanics.md](../../../docs/design/mechanics.md).
- `SurfaceCostTest` (#240) measures what the surface costs a new column of the tall world against the layers alone (ADR 0029 bar: 1.15x). By default it runs a smoke case: a few columns of each of the four test worlds (`tall_baseline`, `tall_surface`, `tall_baseline_biomes`, `tall_surface_biomes`). `DEEPCHARTER_SURFACE_COST=<rounds> tools/gametest.sh 'surface_cost_test*'` measures 289 columns per world and round and prints `[surface-cost]` lines. `DEEPCHARTER_SURFACE_COST_ONLY=<world>` picks one of the four worlds, so each heap reading is the first of its JVM. The ratios and what they show are in [ADR 0036](../../../docs/adr/0036-the-surface-is-generated-from-data-by-a-replaced-overworld-dimension.md). `SurfaceTerrainTest` runs in `deepcharter:surface_sample`, a copy of the shipped overworld in the test preset (the GameTest server bakes a flat overworld).
- Every mod screen must fit the default window (854 x 480, GUI scale 2). `ScreenLayoutClientTest` (#381) opens each screen with its largest content and fails, naming the screen, the widget and the overflow in pixels, when a widget leaves the screen or two interactive widgets overlap. It finds terminal screens through `TerminalTypes.all()` and `TerminalScreens.create`, and container screens through the registered menu types; a new terminal feature or menu type needs a fixture there, or the test says so. A screen that scrolls declares its region with `Case.scrolls`. A screen nothing registers is a case in `standalone()`, and `tools/tests/test_screen_layout_gate.py` fails on one that is not. Keep a per-screen layout test only for what this one does not check.
- A gate that matches source text must match inside the declaration it guards, never a bare mention.
- Before you drive an entity in a far chunk, await entity ticking: `test/support/FarChunks.awaitEntityTicking`. It forces the chunk, so nothing else needs to keep it loaded.
- In a client GameTest, wait with `test/support/ClientWait.until` (or `ClientWait.screen` for a screen), never `context.waitFor` or `waitForScreen`. The client and server tick unthrottled, so a tick budget is a different wall time under load. `until` polls a 120 s wall-clock deadline and its failure names what it awaited and what the client had. The build fails on a `waitFor` in a client test or in the client test support; a deliberate fixed-tick wait carries `// tick-wait: <reason>` on its line or the one above. `tools/tests/tick_wait_gate_check.py` tests this, run by `tools/tests/gate_checks.py` (CI `build` job and pre-push hook). Evidence scenarios are not scanned.
- A world load (`worldBuilder().create()`, `TestDedicatedServerContext.connect()`) is waited on by `test/support/WorldLoadWait`, a 300 s wall-clock deadline whose failure names the stage (connect and login, or world load) and what the client had. Fabric's own wait, `ClientGameTestImpl.waitForWorldLoad` (1200 ticks, "Timeout loading world"), is replaced by `test/mixin/ClientGameTestImplMixin`, a test-only mixin in the gametest mod. `WorldLoadWaitClientTest` fails if a load does not reach it. If a Fabric update breaks the mixin, the client launch fails; fix the target, do not remove the mixin.
- `test/support/MockPlayers` joins a real server-side player with no client behind it.
- A client test that wants its own pod never uses `getEntities(POD).getFirst()`; the colony's wreck pod shares the level. Select by tag, UUID or position.
- `test/support/TwoPlayerServer` starts a dedicated server in a client GameTest, joins the real client, then joins one mock player.
- Wait on entity ticks, not server ticks: chunks far from the players do not tick at first in a fresh world.
- A server GameTest that waits for generated blocks polls under `FarChunks.Deadline`, snapshots chunk state (without loading) before reading blocks, and logs when the wait was needed.
- A test that runs git in a temp repo clears every `GIT_*` variable and sets `cwd` and `GIT_CEILING_DIRECTORIES`; the pre-push hook also unsets them before running tests.

## Client slots

On macOS at most two game clients run at a time (`DEEPCHARTER_CLIENT_SLOTS`, default 2; `1` allows one). `runClient`, `runPlay` and `runClientGameTest` (so also `tools/play.sh` and `tools/record-evidence.sh`) take a machine-wide slot, a lock file in `~/.cache/deepcharter/` (`client.lock` is slot 0). A run that finds both slots taken prints `Waiting for a game client slot (queue position <n> of <m>). Slot 0: <worktree> ... PID <n>; Slot 1: ...` and is served in arrival order. Do not check `pgrep` first. The OS frees a slot when its holder exits or dies, and a waiter that dies leaves a ticket that the others skip, so Ctrl-C and crashes need no cleanup. `tools/play.sh` and `tools/record-evidence.sh` run Gradle with `--no-daemon`, so Ctrl-C of a waiting run ends it. For a direct `./gradlew runClientGameTest`, a Ctrl-C while the run waits leaves the Gradle daemon polling, and it would take a slot with no one watching. After such a Ctrl-C, run `./gradlew --stop` in that worktree. [gradle/clientlock.gradle](../../../gradle/clientlock.gradle) holds the details.

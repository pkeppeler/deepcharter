# Tests

Stubs marked `// Filled by #N` belong to that issue. Tests live in `src/gametest/.../test/`:

- Add test classes and evidence scenarios to the stubs that already exist. `gradle/gametest.gradle.kts` generates the gametest `fabric.mod.json` entrypoint lists from the classes (an `@GameTest` method, `implements FabricClientGameTest`, or `extends EvidenceScenario`) and fails the build for a `*Test` or `*Scenario` class it cannot register; never edit a list. The lists are sorted by name, and no test may depend on that order. A test that swaps a world-global saved record (colony, hangar, repair state, serials) does it through `WorldData.with` or `WorldData.swap` (`test/support`), which set, run the body and restore in a `finally` on the same tick; a direct `getDataStorage().set(` in `src/gametest` fails the build. `WorldDataGuard` stops the server GameTest run if a swap lives into the next tick. `./gradlew runGameTest -PgametestOrder=reverse` runs the server suite in reverse name order to catch a leak. A server stub is `<Thing>Test`, a client stub `<Thing>ClientTest`, a scenario `evidence/<Thing>Scenario` named `m2-<thing>`. A scenario stub throws "stub: #N fills it" when it is selected, and does nothing in a plain run.
- Every Loom run JVM carries `-XX:+ExitOnOutOfMemoryError` and the server GameTest run has an explicit `-Xmx` (`gradle/run-jvm.gradle.kts`, which also says when to re-measure it); `checkRunJvmOom` fails if either is dropped. The server GameTest run takes one of `DEEPCHARTER_SERVER_TEST_SLOTS` (default 2 on macOS) slots, a pool apart from the client slots (`gradle/clientlock.gradle.kts`). A server GameTest runs a body every tick with `TestTicks.each(helper, body)` (`test/support`, called from the test method, where it throws after tick 0), never `helper.onEachTick`, whose per-tick queue the runner keeps until the run ends (#548); the build fails on an `onEachTick` reference in `src/gametest`, and `tools/tests/each_tick_gate_check.py` tests the gate (run by `tools/tests/gate_checks.py`).
- A test that asserts a log line or counter is zero carries a positive control in the same JVM that makes it non-zero by the mechanism under test; a zero with no control passes when the line is reworded.
- A client test that counts a line lag can cause keeps the server calm through the measured window (a small render distance, every chunk in view held on the client) and records the server's tick times per step; checking calm once before counting does not hold it. Calm removes lag as a source, not every race (#1331).
- A test that excuses a known vanilla race decides from the server's own state, captured at the line; its positive control asserts the same predicate fails, not just that the line is not excused (#1331).
- A one-shot check never goes inside `succeedWhen` (or a sequence's `thenWaitUntil`): the poll swallows its exception, and the next poll skips it. Move it to a `startSequence().thenExecute(...)` step, or record it with `test/support/Findings` (`note`, then `ensure(helper)` on every poll). A throw that only forces one more poll carries `// one-shot-ok: <reason>`. The one-shot gate in `gradle/gametest.gradle.kts` catches a `throw`, `fail(`, `assert...(` or `expect...(helper` after a flag set; it does not see a plain local flag, a counter, a tick-number condition, or a check through any other helper, so read those by eye.
- A server GameTest writes a world clock (`setTotalTicks(`, `setPaused(`, `addTicks(`, `setRate(`) only through `TestClocks.paused` (`test/support`, restores in a `finally` on the same tick), or marks the line `// world-clock: <reason>`; the build fails otherwise, and client tests and evidence scenarios are exempt. The scan matches the method name, not the receiver: mark a non-clock `// world-clock: not a clock`. `tools/tests/world_clock_gate_check.py` tests this.
- A catalogue or CRT screen client test clicks and types through `test/support/RealInput` (`click`, `key`, `type`: `MouseHandler.onButton`, `KeyboardHandler.keyPress` and `KeyboardHandler.textInput` with the button and key numbers the window sends, #1304), never a bare number and never the gametest API's direct `mouseClicked` or `charTyped`; pass `InputConstants.MOUSE_BUTTON_*` and `KEY_*`. `type` calls `textInput` directly, past SDL's text-input gate, so it cannot catch a missing `TextInputManager.startTextInput`; only an assertion on `SDLKeyboard.SDL_TextInputActive` can (#1269). Other client tests still use `getInput().pressMouse` (with the constants); move them over when you touch them.
- A client test or evidence scenario hides or shows the HUD only through `ClientChecks.withHudHidden(context, body)` (or `withHudShown`; `withHudHidden(context, ParticleStatus, body)` also sets and restores the particle option), which restores the previous state in a `finally`, also when the body throws; every client test shares one client, so a leaked hidden HUD fails the next test that draws on it. The build fails on a `hud.toggle()`, `keyToggleGui`, `hideGui` or `KEY_F1` elsewhere in `src/gametest`; a deliberate toggle carries `// hud-toggle: <reason>` on its line or the one above. `HudHiddenClientTest` proves the restore, and `tools/tests/hud_toggle_gate_check.py` tests the gate (run by `tools/tests/gate_checks.py`).
- A client test that reads pixels of the surface sky takes its screenshot through `ClientChecks.skyShot` (minimal particles, HUD hidden): the sky's `dust_mote` ambient particle is dark and random (#1043).
- A pixel test compares against a reference read from the same frame (the region the criterion is about, such as the walls a cover must blend into), never against the value the code under test builds its own colour from: that only proves the code drew what it was given (#1188).
- A test's Javadoc claims only what its assertions check; a claim no assertion would fail on is deleted or given an assertion.
- A test or scenario gets a layer's level, and turns a layer and a local Y into a world position, only through `TestLayers` (`test/support`: `level`, `band`, `isIn`, `clientIsIn`, `dimension`, `worldY`, `pos`, `vec`). A layer is a band of the campaign level: `level(n >= 1)` is the overworld when its type is the campaign type, otherwise `deepcharter:campaign_sample`, and `TestLayers` fails if a layer ever resolves to a layer dimension; `worldY` is the band's `minY()` plus the local Y (a layer's rows are counted from its floor), and the surface keeps its own Ys. A test never carries a Y from one layer to another: ask `worldY` of the layer it stages in. A crossing is in place (ADR 0061): a test that crosses a floor first puts the player or pod in the layer above (a crossing is read from the layer last seen), cuts the shaft, and opens a pocket under the crust with `RoomCarver.carvePocketBelow`, because the rows under a layer's floor are the next layer's rock. A literal world Y or `LayerChain.dimension(` elsewhere in `src/gametest` fails `checkFixedPosGate` (see [evidence.md](evidence.md)).
- A test or scenario asks `TestLayers.band(level, layer)` (a `LayerChain.Band`) for a layer's `minY()`, `maxY()` and `height()` and `TestLayers.isIn(entity or pos, layer)` whether something is in a layer, never `getMinY()`, `getMaxY()` or `getHeight()` of the level: a layer is a band of the campaign level, so the level's height is every layer's. A raw level-height read in `src/gametest` outside `TestLayers` fails `checkFixedPosGate` unless it is about the level and not a layer (the Nether, a whole test world) and carries `// level-height: <reason>` on its statement or the comment lines above it; `tools/tests/fixed_pos_gate_check.py` tests it.
- A layer test's floor and ceiling Ys come from `TestLayers.worldY` (or a constant built with it): a bare `int floor = 60` stages in the surface band and passes. `checkFixedPosGate` fails an int or long named `*floor`, `*ceiling` or `*roomY` set to a literal unless it ends with `// fixed-pos: <reason>` (an offset or a size, not a Y).
- Layers share one level, so give each layer's cells their own chunk columns when two sites would share one: a second visit to a column finds its chunks already sent. After a level change into the tall level a client test waits for `client.gui.screen() == null` (the loading screen) and an idle server before the next step.
- `StructureLightBorderTest` (#824) shows that `LightSync` sends a player who already holds a chunk of a hold its settled light when the hold ends (read through `LightSyncSends`, so a vanilla update cannot stand in), and that the server's stored light is the light `test/support/BlockLightOracle` works out from the blocks alone, checked before the lamps are removed. Use the oracle for any test of stored block light; do not compare the light engine with itself.
- `LightSyncRingHoldTest` (#494) pins `LightSync`'s ring hold: a neighbour of a drawn chunk is not sendable while the light tasks queued at the drawn chunk are waiting (vanilla's hold waits only per position). Two cases hold the drawn chunk's wait back with `LightEngineGate` (with `LightEngineGateMixin`, test only), so the state is set, not sampled; the sampled case alone could pass vacuously. A third brings a mock player into view of a neighbour whose send is extended and asserts the chunk reaches them. Disabling the `addSendDependency` in `LightSync.dependOn` fails the gated and sampled cases; disabling `offerWhenSendable` fails the player case.
- `LightSyncSafetyNetTest` (#863) pins `LightSync`'s safety net: `LightBroadcastSuppression` (with `ChunkHolderLightSuppressMixin`, test only) makes vanilla's light broadcast mark nothing for a chunk, so a light change after a hold reaches a player only through the net, which the test reads through `LightSyncSends`. A mock player is sent chunks only if its destination chunk ticks, so the test forces the chunks and waits for the player's chunk to tick before it teleports. The light engine publishes on its own thread in wall time, so a case that needs a light to come and go in a few ticks has no fixed tick budget: wait for the stored light to stop changing, and align a case to the net's schedule instead of racing it. A safety-net or resend test must include the transient case: the state at the send is neither the state before nor the state after, and the state returns to an earlier one between two samples.
- A creature that joins a sonar tag brings the attribute the tag's contract needs (`FOLLOW_RANGE` >= `SonarTuning.noiseBlocks` for `sonar_hears`); a test over the shipped tag (`PodSonarTest`) checks it. The gametest mod's own tag lines (husk, cow, pig, sheep) are there for tests only: a test that adds one of those mobs discards it on every path, pass or fail.
- A mob a server GameTest leaves standing is built with `TestEntities.mob`, not `create`, unless it stays within 32 blocks of a player for its whole life: `Mob.checkDespawn` removes an idle monster farther off, and a removed mob keeps its path "in progress" (#1234).
- A GameTest that cuts air into generated layer rock calls `RoomSeal.seal` first (generated lava and gas flood the cut otherwise).
- A tuning knob that counts blocks beyond a box says whether the edge cell is inside, and a test pins both sides (N in view, N+1 out).
- A leak guard that counts a proxy (tickets for chunks, instances for memory) says in its comment what the proxy cannot see, and a blindness guard anchors on a marker the test itself holds, not on mod behaviour.
- A feature registered on a Fabric tick or lifecycle event (a server tick, CHUNK_LOAD, join, a charter event) has a test where the real tick or event produces the effect, with no direct call of the handler it registers. Reload a real chunk, or wait on the real tick.
- A change that lets any entity spawn naturally in a layer dimension pins `SPAWN_MOBS` false in every test and evidence world that enters that layer, via one shared setup (`test/support/TestPacks` sets it when each server starts).
- Run one client GameTest class with `./gradlew runClientGameTest -PclientTests=<filter>` or `tools/gametest.sh --client <filter>`. The filter is a comma-separated list of class names (simple or fully qualified) or globs (`Pod*ClientTest`; `*` matches any characters), matched against the client list that `generateGametestModJson` writes, and it also selects evidence scenarios. A term that matches no client class fails the build and names the term, so a typo never runs nothing and reports green. Without the property the list is the full one. The property is an input of the generation task, so changing it regenerates the list. `-PclientShard=i/n` then keeps the i-th of n shards of that list, balanced by the seconds in `gradle/client-test-weights.txt` (a class not listed counts 10 s, so a new class needs no entry and every class is in exactly one shard; a malformed spec or an empty shard fails). CI runs the matrix in `client-tests.yml`; `tools/tests/test_client_shards.py` checks it. The `client-gametest` aggregate checks the shards merged the same main and records it (`tools/ci-shard-main.sh`, tested by `tools/tests/ci-shard-main.test.sh`). A later plain `./gradlew build` or `runClientGameTest` regenerates the full list. `tools/tests/client_filter_gate_check.py` tests this, run by `tools/tests/gate_checks.py` (CI `build` job and pre-push hook).
- Run one GameTest, or a prefix of them, with `tools/gametest.sh '<test_id or prefix*>'` (quote the `*`). It runs `./gradlew runGameTest` from the repo root it lives in, sets the filter through `JAVA_TOOL_OPTIONS` (a bare `-D` on the Gradle command line is ignored), and fails when no test matches.
- `SeamSwapTest` (#1229) covers the seam swap and its recovery on the server, with mock riders that answer the prepare as a client does. `SeamPodScene` (shared with `SeamSwapClientTest` and `SeamAdoptionClientTest`) is a pod with the mock in seat 1 and the real client in seat 2, held over the floor and then dropped. `SwapProbes` counts what a vanilla respawn does and a swap must not (loading screen, `SoundManager.stop()`, respawn packet), and `TwoSeatPods` gives a test pod a second seat, since pods seat one. `SeamSender.setVanished` makes one chunk not loaded for `resendCarved`, to pin its fallback.
- `LavaBoreTest` (#231) is a measurement more than a regression test. By default it runs a 2-bore smoke case in seconds. `DEEPCHARTER_LAVA_BORES=<n> tools/gametest.sh 'lava_bore_test*'` runs <n> full bores of layer 1 (about 2.5 minutes for 100 on an 8-core M2) and prints `[lava-bore]` lines. `DEEPCHARTER_LAVA_BORES_LINING=<slabs>` makes the bot line (#313), and `DEEPCHARTER_LAVA_BORES_BRICKS=<n>` sets its starting bricks. `DEEPCHARTER_LAVA_BORES_LINER=<tier>` (#339) gives the pod a liner part of that tier instead and is measured alone: it is an error together with `_LINING`. `DEEPCHARTER_LAVA_BORES_PACK=<n>` puts that many bricks in a liner pilot's pack. The bot brakes in a fall; `DEEPCHARTER_LAVA_BORES_BRAKING=off` turns that off. `DEEPCHARTER_LAVA_BORES_BRACE=1` (#378) gives the pod the breach brace part. `DEEPCHARTER_LAVA_BORES_SHIELD=1` (#482) gives it the heat shield part (with a rack of `_BRICKS` and a pack of `_PACK`), and `DEEPCHARTER_LAVA_BORES_PILOT=leave|ignore` picks the pilot: `leave` climbs out of lava half a second after contact and turns back alive (lining by hand if it is trapped under rock), `ignore`, the default, never reacts; the run prints a `[lava-bore] summary:` line of the figures a design table reads. `DEEPCHARTER_LAVA_BORES_SOUNDER=<tier>` (#373) gives the pod the real seep sounder part of that tier (1 or 2); the bot then reacts only to what the part tells it (its HUD state and range) and steps aside from the pocket it shows, and the part bleeds what the bot drills into; it is an error together with a `_GAS` other than `ignore`. `DEEPCHARTER_LAVA_BORES_GAS=avoid` (#368) makes the bot step aside from a gas pocket that a tier 3 scanner (`ScannerTuning.gasTier`) would show in its next slab; `ignore`, the default, bores straight through; `sounder1` and `sounder` are design bounds, not counterplay the game has (the bot knows every pocket of its footprint in the 2 slabs below; `sounder` also knows the step's cells and tries all four sides). `DEEPCHARTER_LAVA_BORES_CHARGES=1` (#509) makes the bot set a blasting charge from the seat (the real item and use path) and hover clear of it, instead of sidestepping Company rock, and prints a `[lava-bore] charges` block; every run prints the `straight shafts` line. `DEEPCHARTER_LAVA_BORES_CONSOLE=<tier>` (#502) models the signal decay: the pod carries a console of that tier (0 is the stock one, still decayed; unset is no decay at all, as before), and the bot reads the plate (the sounder's line, the brace's prompt, the crust warning) and the scanner's window (the lava the lining bot looks for) only on ticks the decay leaves them readable; a Mole's cap makes 2 the top tier it can fit. `DEEPCHARTER_LAVA_BORES_HEED=1` makes a pilot without a brace turn back, alive, when the plate shows the crust warning. A decayed run prints a `[lava-bore] decay` line and a `decay depth` line. The cause tally is priority-ordered: lava, then gas, then charge, then landing, then crust. The numbers are in [mechanics.md](../../../docs/design/mechanics.md).
- `SurfaceCostTest` (#240) measures what the surface costs a new column of the tall world against the layers alone; its ratio is tracked, and the bar is per band in `CampaignCostTest` ([ADR 0086](../../../docs/adr/0086-each-campaign-band-is-held-to-one-layers-cost-per-row-and-the-whole-worlds-ratio-is-only-tracked.md)). By default it runs a smoke case: a few columns of each of the seven test worlds (`tall_baseline`, `tall_surface`, `tall_baseline_biomes`, `tall_surface_biomes`, and for the features of #245 `tall_surface_bare`, `tall_surface_yard`, `tall_surface_yard_bare`). `DEEPCHARTER_SURFACE_COST=<rounds> tools/gametest.sh 'surface_cost_test*'` measures 289 columns per world and round and prints `[surface-cost]` lines. `DEEPCHARTER_SURFACE_COST_ONLY=<world>` picks one of the seven worlds, so each heap reading is the first of its JVM. `tools/cost-run.sh <rounds> <world>...` (#473) measures worlds one JVM each, keeping the machine load beside each reading (limits and verdict in its header). A `bare` world is the same surface with every biome's features taken out, so the ratio of a world to its bare twin is what the features (stalks; the salvage crates in the yard worlds, which put every column in the yard) cost alone. The ratios and what they show are in [ADR 0036](../../../docs/adr/0036-the-surface-is-generated-from-data-by-a-replaced-overworld-dimension.md) and, for the features, [ADR 0047](../../../docs/adr/0047-the-surface-has-no-ore-the-bootstraps-metal-is-salvage-and-the-yard-is-a-biome.md). `SurfaceTerrainTest` and `SalvageBootstrapTest` run in the surface band of `deepcharter:campaign_sample` (the GameTest server bakes a flat overworld, of the short `deepcharter:test_overworld` type, so the shipped overworld is only in the test pack's copy; a client test in a default-preset world has the real one).
- `deepcharter:campaign_sample`, where the layer tests run, is the shipped overworld with its density set to air below 32 rows under the last layer's floor (y -800 today), so a chunk does not generate 1488 rows of unbuilt rock (#823, [ADR 0087](../../../docs/adr/0087-the-test-pack-campaign-sample-leaves-the-unbuilt-depth-as-air.md)). A test that asserts on the unbuilt depth's terrain or blocks, or on whole columns of generated terrain, runs in `deepcharter:campaign_full`, the exact copy of the shipped overworld; the unbuilt depth's biome and its attributes are the same in `campaign_sample`. `CampaignTerrainTest` (#742) runs in `campaign_full`, the test pack's copy of the campaign world, which is the shipped overworld since #803: bands, rock, crust, zone biomes, and every data file's band edge against `layer/CampaignBands`. Read a biome from the chunk's stored cell, never `level.getBiome` (it blurs a band edge). `CampaignContentTest` (#743) covers what the world holds besides terrain: structure sites, the Prospector wreck, the Conduit, cave stalks, figure spawns and every placed feature's height range against its band; the ore tables run in `OrePlacementTest` on both the layers and `campaign_sample`. `CampaignCostTest` gates the campaign generator, measured in `campaign_full` (the shipped world; the air-filled `campaign_sample` would measure the wrong thing), per band ([ADR 0086](../../../docs/adr/0086-each-campaign-band-is-held-to-one-layers-cost-per-row-and-the-whole-worlds-ratio-is-only-tracked.md)) with `test/support/ColumnCost` (shared with `SurfaceCostTest`) and `test/support/BandCost` (the arithmetic, which `BandCostTest` checks on made-up readings). `DEEPCHARTER_CAMPAIGN_COST=<at least 4> tools/gametest.sh 'campaign_cost_test_each_band*'` measures; the gate judges only a full pool (`BandCost.Pool.judged`: `BandCost.RUNS` runs of one tree with as many rounds each, `BandCost.ROUNDS` in all), so run it that many times with `DEEPCHARTER_CAMPAIGN_COST_POOL=<absolute file>`. `DEEPCHARTER_CAMPAIGN_COST_ONLY=<world[,world]>` picks worlds (`tools/cost-run.sh` reads `[surface-cost]` lines only, so it does not run this test). Read the per-round pairs: readings drift upward on a loaded Mac.
- A worldgen change that must leave the world identical (a speed cut) is proved with `CampaignWorldHashTest` (#743): `DEEPCHARTER_WORLD_HASH=<file> tools/gametest.sh 'campaign_world_hash_test*'` on the tree before the change (a detached `git worktree`, the test copied in) and on the tree after, then `diff` the two files. It writes one line per chunk, a hash of every block state by name and properties and of every biome cell by key, never by registry id; a before and after run must not differ.
- `CampaignCrossingTest` (#745, ADR 0061) runs in `campaign_sample` too: it drives a mock player's or a pod's Y across the band boundaries and counts `BreachEvents.CROSSED` (`from == to` there), then checks the transmission, handbook chapter 8, the hymn and the deepest point, and that a towed pod is not carried. `BreachHudTest` covers the client side, a rumble with no fade.
- The test mod's `flat_all_dimensions` preset is generated (#1158): edit `src/gametest/templates/world_preset/flat_all_dimensions.json`, never a file under `build/`. An entry `{"$from": "minecraft:overworld", <key>: <value>}` is the shipped `overworld.json` with those top-level keys replaced (`campaign_full` and every `campaign_<band>` window and floor); `generateGametestPreset` fails the build on one of those names written out as a copy, so the windows follow the campaign generator. `CampaignCostTest.theWindowsAreTheCampaignWorldCutToTheirBands` stays the guard.
- Every mod screen must fit the default window (854 x 480, GUI scale 2). `ScreenLayoutClientTest` (#381) opens each screen with its largest content and fails, naming the screen, the widget and the overflow in pixels, when a widget leaves the screen or two interactive widgets overlap. It finds terminal screens through `TerminalTypes.all()` and `TerminalScreens.create`, and container screens through the registered menu types; a new terminal feature or menu type needs a fixture there, or the test says so. A screen that scrolls declares its region with `Case.scrolls`. A screen nothing registers is a case in `standalone()`, and `tools/tests/test_screen_layout_gate.py` fails on one that is not. It also renders each screen once through a recording `GuiGraphicsExtractor` (`test/support/DrawnText`, #411) and fails, naming the screen, the string and the overflow in pixels, when text the screen draws itself (`graphics.text`, `CrtDraw.glowText`) leaves the screen or a declared scroll region, or overlaps an interactive widget; text drawn inside a widget's own render is the widget's and is skipped, and the typewriters are finished first. `textWithWordWrap` is not recorded. A screen draws text only inside its own extract method or inside a widget; `addRenderableOnly` and custom `Renderable`s are refused, because the drawn-text gate skips text under any non-Screen `Renderable`. The Python gate takes the transitive closure of screen classes (`extends PanelBase` counts) and fails on a `setScreen(make())` factory not listed in `FACTORIES`. Keep a per-screen layout test only for what this one does not check.
- A paged screen's layout case visits every sheet, by walking with Next, not with `goTo(page)`, and builds its content at its largest (e.g. `ShippedHandbook.everyChapterFull`).
- A client test that reads a screen's text through `DrawnText.of(screen, x, y)` parks the cursor off every item first (`CatalogueScene.parkCursor`): a hovered item's tooltip or name is recorded with the rest and sits in no panel.
- A test that checks a sprite is drawn by `DrawnSprites` also checks that the sprite resolves: `client.getAtlasManager().getAtlasOrThrow(AtlasIds.GUI).getSprite(id)` is not the missing sprite (`MissingTextureAtlasSprite.getLocation()`). The recorder sees the id, not whether the atlas has it.
- A gate that matches source text must match inside the declaration it guards, never a bare mention.
- A non-private member of `src/main` or `src/client` that only `src/gametest` references fails `checkTestOnlyMembers` (part of `check`): delete it and test through the seam production uses, or make it private. A deliberate, permanent seam carries `// test-seam: <why it is deliberate>` on its declaration line or the comment line above. A `static final` field of a registered game object (Block, Item, EntityType and the like) and an abstract method are exempt.
- A client test that stages a pod or terminal in a chunk it just loaded waits until the chunk is entity-ticking (`isPositionEntityTicking`) before it acts: until then the pod is not in the level and a server lookup of it (the pump's, the processor's) finds none (`OutpostClientTest`).
- A server `@GameTest` in the `campaign_sample` world names one of the batches in `CampaignEnvironments` (`test/support`), `environment = CampaignEnvironments.<constant>`, so the campaign tests do not share one batch's live chunks (#957); the scan in `generateGametestModJson` fails the build without one, and a new batch is one constant plus a `test_environment` JSON. A dimension spelled as a string literal fails the scan too: name it with a constant.
- A test that reaches the campaign level only through `TestLayers` names no dimension and runs in a default batch, so every batch is capped: `GameTestBatchFactoryMixin` replaces vanilla's 50 tests with `TestBatches`' caps (#1026), and `TestBatchesTest` checks the batches that came out. `gameTestHeap` is measured with them. A batch-cap raise or tall-world addition that leaves the GameTest heap under 2x the measured peak raises `gameTestHeap` in the same PR.
- A server GameTest that reads state a neighbour in its batch can change (a trigger counting every player in range, a server-global setting) gets an `environment` of its own: batches run one after another, and a batch lays its tests 5 blocks apart, so a neighbour's mock stands about 11 blocks from this test's blocks (#1368). One id per test; reusing another test's id puts them back in one batch (#1383).
- A `test-seam` whose only future caller is an open issue is not a seam: defer the member to that issue, or name the permanent reason.
- A `FarChunks.awaitEntityTicking` callback only sets state; it never calls `runAfterDelay` or registers ticks. Wait on that state with `helper.startSequence().thenWaitUntil(...)` and run the test body in `thenExecute` steps.
- Before you drive an entity in a far chunk, await entity ticking: `test/support/FarChunks.awaitEntityTicking`. It forces the chunk (a ticket only, see below), so nothing else needs to keep it loaded, and `GameTestInfoMixin` lets it go when the test finishes (#569). The force-chunk gate (`gradle/gametest.gradle.kts`, part of `generateGametestModJson`) fails any `setChunkForced`, `updateChunkForced` or forced ticket in `src/gametest` outside `FarChunks`. A test never forces or releases a chunk directly: force with `FarChunks.force(helper, level, x, z)` (or `awaitEntityTicking`), release early with `FarChunks.release(helper, level, x, z)`, and pin the colony pad with `FarChunks.pin`. The runner unforces every forced chunk at each batch end; a pinned chunk is exempt (`ServerLevelForcedMixin`), and nothing else is, so a force that must outlive a batch is a pin. Never release or unload-cycle a pinned chunk: it stays forced. A case with no `GameTestHelper` (a client test, an evidence scenario) is marked `// force-ok: <reason>`. A chunk left forced pins up to 17 x 17 chunks of proto chunks for the rest of the run, which is what filled the heap. A loaded chunk (`whenBlocksLoaded`) is enough for blocks only; a crossing or spawn into one needs `awaitAllEntityTicking` (#1151).
- A client-test fill or command that skips unloaded chunks silently (`fillbiome`) forces its box first and reads the result back after; a fix that only logs is not a fix.
- `AtmosphereScenes.stand` is the evidence scenario's and keeps its fixed settle; a full-frame still uses it. `standWithoutSettle` is the client test's: it waits for the client's player, chunks, light and `hasRenderedAllSections`, then for a steady picture. The steady-picture check reads only the centre of the screen, so never rely on it for meshing.
- In a client GameTest or evidence scenario, wait with `test/support/ClientWait.until` (or `ClientWait.screen` for a screen), never `context.waitFor` or `waitForScreen`. The client and server tick unthrottled, so a tick budget is a different wall time under load. `until` polls a 120 s wall-clock deadline and its failure names what it awaited and what the client had. The build fails on a `waitFor` in a client test, in the client test support or in `test/evidence/`; a deliberate fixed-tick wait carries `// tick-wait: <reason>` on its line or the one above. `tools/tests/tick_wait_gate_check.py` tests this, run by `tools/tests/gate_checks.py` (CI `build` job and pre-push hook).
- A client test that boards a rider and then presses a key or takes a screenshot first waits on `ClientWait.chunksAround` for every chunk the riders stand in (#1082): the server tracks an entity for a client only after sending it that entity's chunk.
- A world load (`worldBuilder().create()`, `TestDedicatedServerContext.connect()`) is waited on by `test/support/WorldLoadWait`, a 300 s wall-clock deadline whose failure names the stage (connect and login, or world load) and what the client had. Fabric's own wait, `ClientGameTestImpl.waitForWorldLoad` (1200 ticks, "Timeout loading world"), is replaced by `test/mixin/ClientGameTestImplMixin`, a test-only mixin in the gametest mod. `WorldLoadWaitClientTest` fails if a load does not reach it. If a Fabric update breaks the mixin, the client launch fails; fix the target, do not remove the mixin.
- Each client test class has a 180 s wall-clock limit (#434): `ClientTestLog.start(this)` arms `test/support/ClientTestWatchdog`; `startUntimed(this)` is for a class that is long by design (the evidence scenarios). `DEEPCHARTER_CLIENT_TEST_SECONDS=<n>` changes the limit (`0` turns it off). Past the limit the run logs `CLIENT-GAMETEST TIMEOUT <class>` with every thread's stack and exits 1. `WatchdogHangClientTest` hangs on purpose under `DEEPCHARTER_HANG_FIXTURE=1`. Diagnosis: #434.
- `test/support/MockPlayers` joins a real server-side player with no client behind it. Custom payloads the server sends are recorded: call `MockPlayer.announceChannel(type)` first, then read them with `payloadsOf`; this is a payload object, so it does not exercise the codec: round-trip `CODEC` separately.
- The runner keeps every finished `GameTestInfo` for the whole run, so a callback still pending when a test ends (the next-tick entry of `TestTicks.each`) kept its mock `ServerPlayer` and its `PlayerAdvancements` alive; `GameTestTickerMixin` now clears every done test's pending callbacks and sequences, however it finished (#656). `MockPlayersTest.finishedTestDoesNotRetainItsMock` guards it, and needs no other test: it builds its own never-run `GameTestInfo` probes, ends them from an end-of-tick event and hands them to `GameTestTicker.SINGLETON`, so it passes alone, in any batch layout and in any order (#1163).
- A server GameTest whose sequence asserts must not run inside a helper that calls `helper.succeed()`: a finished test drops its sequences, so their assertions never run (#993).
- `ChunkMapUnloadMixin` (always on, test mod; why and what else it changes: its Javadoc) gives `ChunkMap.processUnloads` unlimited time, and `ChunkMapSaveMixin` (always on) skips saving half-generated chunks (#816). `ChunkUnloadTest` guards both. A chunk-unload timing bug may not reproduce in GameTests.
- A level's `EntityTickList` keeps its `passive` map, a snapshot of every entity ticking at its last change made during an iteration, so a removed player stays on the heap until another such change; `MockPlayers` empties it at the end of a tick in which a mock left (`TickLists`, #723).
- A mock's `leave()` disconnects its `Connection`, not just `player()`: a respawn swaps the `ServerPlayer` under the same listener, and Fabric ends its networking addon (which its registry holds) only on that disconnect. Respawn a mock with `connection.handleClientCommand(PERFORM_RESPAWN)`, not `PlayerList.respawn` (it leaves the listener on the dead player). A Fabric event cannot be unregistered, so a listener a test registers captures ids and plain values, never a `MockPlayer` or `ServerPlayer` (#698).
- `test/support/PacketJitter` makes the client skip every Nth tick's entity moves and replay them a tick later (the harness ticks server and client in lockstep, so it never drifts by itself); `test/mixin/ClientPacketListenerMixin` is its test-only hook, inert until `start` and ended by `stop` in a `finally` (#961). `PacketJitter.stall(n)` holds every move for `n` client ticks and hands them over in one, a server that runs late (#1041, ADR 0082); `PacketJitter.movelessTicks()` counts client ticks in a row with no move; `test/support/PodDrives` re-runs a steady drive that saw more than 6 (#1168). `PodDriveStepTest` is the server-side guard that a drilling pod never moves further in a tick than its speed.
- A static listener's per-test state is removed on every exit path of the test, including a throw and a timeout, not only on success: hook `GameTestInfoMixin`'s `finish` (as `FarChunks.release` and `ItemSpawns.release` are) instead of relying on the test's last step (#967). For an entity or state a test leaves outside its box, register `TestCleanups.onFinish(helper, ...)`; it runs from the same `finish` hook.
- After a server `setPos` a pod's `onGround()` stays true until its next tick, so it is no landing wait (#893). The cockpit altimeter is decay-garbled at low hull, so a still never proves a position (#893).
- Pod movement ignores `Entity.setNoGravity` (#554): hold a pod still with a `PodEvents.AFTER_TICK` pin (see `TwoPlayerClientTest`).
- Swap a world-global record only through `WorldData` (a gate enforces it; `WorldDataGuard` watches only the dedicated GameTest server). Read loaded chunks through `scanner/LoadedBlocks`.
- A server GameTest throws `failure(helper, format, args...)` and checks with `expect(helper, condition, format, args...)`, static imports from `test/support/Failures`: it formats the message because `helper.assertionException(String, Object...)` leaves `%s` unfilled. Use `%s` placeholders, never concatenation; a new printf-style helper needs `@FormatMethod`/`@FormatString` (`AnnotateFormatMethod` is on). A test never declares `failure`, `fail`, `expect` or `require` over a boolean (`generateGametestModJson` fails it); a client test uses `ClientChecks.require(condition, message)`. Only a `messageOf` helper and an `expect` comparing `what`, `expected` and `actual` stay local.
- `-PclientTests=<server test class>` fails the build, and `-PclientTests` never runs evidence scenarios (use `tools/record-evidence.sh <scenario>`). A client-GameTest failure on CI uploads `build/run/clientGameTest/screenshots` (`gh run download <id>`).

- Before you write a new bore bot (a pilot's `Input`s, a sidestep `Side`, a lining check) or a scenario camera helper (a structure-axis `at`), look in `test/support` (`BoreBot`, and `Inputs` for the shared pod inputs `FORWARD`, `JUMP`, `FORWARD_JUMP`, `SNEAK` and `SPRINT`) and `EvidenceScenario` and in the nearest sibling test or scenario, and extract there if a second copy would appear.

- `test/support/SeamSite` is the site of a seam test on the shipped layer_1 to layer_2 crossing (a column of layer 1, the area of layer 2 under it, a thousand blocks from the next test's, and the wait for the area); `SeamStreamingTest` and `SeamDataAheadTest` share it, and each gives its tests their own site indexes. `MockPlayer.setViewDistance` raises the view a mock asks for (it asks for 2), `timesSentIn` and `chunksSentIn` count chunk packets by the level the client was in, `forgetsAfterRespawn` lists the forgets after the latest respawn, and `send` sends the server a C2S payload. The test server's own view distance is the seam's send radius (3), so a crossing test sees no chunk beyond the area. `test/support/ChunkPacketLog` and its hook in `ClientPacketListenerMixin` log the chunk packets the client handles, inert until `arm` and ended by `disarm` in a `finally`; `SeamAdoptionClientTest` uses them and logs a `SEAM-TIMING` line for the adopted and the fallback crossing, with no frame budget (CI renders in software).
- `test/support/TwoPlayerServer` starts a dedicated server in a client GameTest, joins the real client, then joins one mock player.
- Wait on entity ticks, not server ticks: chunks far from the players do not tick at first in a fresh world.
- `FarChunks.force` takes the ticket only; the chunk loads on the worker threads. Wait with `awaitEntityTicking` or `FarChunks.whenBlocksLoaded(helper, BlockSurvey.area(level, n), body)`; never call a synchronous `getChunk` on the server thread in a server GameTest, which starves its batch (#1016). `BlockSurvey.find` reads loaded chunks only; `generateAndFind` is for client evidence code. A case that must load under a same-tick `WorldData.with` takes `environment = CampaignEnvironments.SYNC_CHUNK_LOAD`.
- Await entity ticking for every chunk a test pod, player or corridor works into, not only the start chunk, and start the drive or the hazard (lava, a timed tick) in the `then`: a chunk that ticks late runs its overdue ticks at once (#1083).
- A server GameTest that waits for generated blocks polls under `FarChunks.Deadline`, snapshots chunk state (without loading) before reading blocks, and logs when the wait was needed.
- A test that runs git in a temp repo clears every `GIT_*` variable and sets `cwd` and `GIT_CEILING_DIRECTORIES`; the pre-push hook also unsets them before running tests.
- `ScannerFrameTimeClientTest` (#537) is a measurement, not a regression guard and not a pass line (it asserts only that the panel is drawn): it logs `[scanner-frame]` lines, the CPU milliseconds of one frame's render-state extraction (the HUD with its scanner panel) at the top scanner tier on a full-rock area, with no scanner, with one, and with the HUD hidden as a control. It unpaces the client (no vsync, no frame limit) and restores both. Do not time a client tick (it waits for the 20 ticks a second) or `renderFrame` (it returns at once in a test, drawing nothing).
- A visual-legibility test measures at the on-screen cell size of the smallest shipped window, not at the unscaled tile.
- A test that restates a registry (a hand-copied list of names) is not a test; read the registry.
- A render-path feature with its own update loop (`FloodlightBeams`) needs a client GameTest driving it, not only an evidence scenario.
- A client-only part with logic (a finder, a picker, a ticker) keeps that logic in a class in `src/main` that takes a `LevelReader`, so a server GameTest runs it. The client holds only the wiring, and a client GameTest covers the wiring (#878: `HornSearch`, `SpotPicker`).
- A change to shared client visuals runs every client test class that reads them, not only its own (#630 missed `TextureLayersClientTest`).
- A control assertion must be shown to fail without the feature in every scenario it runs; a case that passes by closeness to a dark control is a log row, not an assertion.
- A cadence or cap test drives the production tick path (the look, the roll, the count, the cap); a test that samples a helper the tick calls, or asserts arithmetic on tuning constants, is a log of the numbers and not a test of the cadence (`DrifterSpawnTest.theTickPlacesDriftersByPodsUpToTheZoneCap`).
- Prove a regression test with a mutation check: break the code under test in your worktree, see it go red, revert (#627's first case was vacuous).
- A test Javadoc that names the mutations it catches states only mutations that were run red; a reviewer re-runs at least one.
- A count or window derived with `ceil`/`floor` from tuning floats must not sit on an integer boundary that float widening decides; write the strict-inequality form (`floor(x) + 1`) and say which side the boundary falls (#1356: `0.2f` widened to 0.20000000298 gave `ceil` 4 where a real 0.2 gives 3).

- Gradle runs with the configuration cache on in every worktree: `gradlew` gives each checkout its own daemon registry (`.gradle/daemon-registry`, #1120), so a configuration cache entry never names another worktree's scripts, and `--no-configuration-cache` is not needed for concurrent worktrees. Memory model: one daemon (`-Xmx2G`) per active worktree, gone 10 minutes after its last build. A Gradle started another way (an IDE, a bare `gradle`) shares one daemon again. `tools/tests/gradle-worktree-isolation.test.sh` guards this.
- A test guard that skips on a missing local tool fails under `CI=true` instead, or names the CI step that guarantees the tool (as `tools/install-ffmpeg.sh` does for libvorbis).

## Client slots

On macOS at most two game clients run at a time (`DEEPCHARTER_CLIENT_SLOTS`, default 2; `1` allows one). `runClient`, `runPlay` and `runClientGameTest` (so also `tools/play.sh` and `tools/record-evidence.sh`) take a machine-wide slot, a lock file in `~/.cache/deepcharter/` (`client.lock` is slot 0). A run that finds both slots taken prints `Waiting for a game client slot (queue position <n> of <m>). Slot 0: <worktree> ... PID <n>; Slot 1: ...` and is served in arrival order. Do not check `pgrep` first. The OS frees a slot when its holder exits or dies, and a waiter that dies leaves a ticket that the others skip, so Ctrl-C and crashes need no cleanup. `tools/play.sh` and `tools/record-evidence.sh` run Gradle with `--no-daemon`, so Ctrl-C of a waiting run ends it. For a direct `./gradlew runClientGameTest`, a Ctrl-C while the run waits leaves the Gradle daemon polling, and it would take a slot with no one watching. After such a Ctrl-C, run `./gradlew --stop` in that worktree. [gradle/clientlock.gradle.kts](../../../gradle/clientlock.gradle.kts) holds the details.

- A client GameTest JVM holds up to 4 GB of heap (`clientGameTestHeap`, `gradle/run-jvm.gradle.kts`, which has the measured live set), so two of them fit a 16 GB Mac. A world that outlives its test class is a leak (the 4 GB is margin until #914 is fixed): `FarChunksReleaseClientTest` fails when a stopped world's pinned chunks are still held, and the client run's histograms and thread lists (`client-gc-log` artifact) show the type or thread that grows. A static collection of a test (support or listener) must not hold a `ServerLevel`, a player or a chunk past `SERVER_STOPPED`. A dedicated server a client test starts goes through `DedicatedServerRelease.createServer(context, properties)` (test/support), never `worldBuilder().createServer`; the gametest source gate fails a raw call. It sets `max-tick-time=-1` (no watchdog thread), and with its `System.in` and shutdown-hook release lets a stopped server be collected; `DedicatedServerReleaseClientTest` guards it (#914). The trade-off: a server that hangs after the world loads no longer gets the 60 s watchdog crash and thread dump; `ClientTestWatchdog` (180 s per class, full thread dump) catches it.
- A client GameTest or evidence scenario ends on the title screen: Fabric's runner throws "did not finish on the title screen" otherwise. A test that opens a screen over the title screen, or leaves a world, closes it (`OldWorlds.backToTheTitleScreen` for the refusal screens).

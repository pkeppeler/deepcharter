# Merging

A `gameplay` PR also needs the `px-reviewed` label, which `tools/mark-review-passed.sh` and `tools/merge-pr.sh` (so the batch and queue too) check; the rule is in [CLAUDE.md](../../CLAUDE.md).

Merge only through `tools/merge-pr.sh <n>`, which refuses and gives the reason. It merges the PR as a batch of one (`tools/merge-batch.sh <n>`, below; [ADR 0113](../../../docs/adr/0113-single-prs-merge-as-a-batch-of-one-and-the-roadmap-rides-in-the-landing.md)): the PR's own CI need only be green, not current, and the CI on its merged tree is the proof. `tools/merge-pr.sh <n>` exits 3 when another batch or queue holds the merge lock: nothing was merged, retry later. `tools/merge-pr.sh --direct <n>` is the older merge through GitHub's merge endpoint (the PR shows as merged) and what the queue calls. It retargets open PRs stacked on the PR's branch to its base first, because GitHub deletes the head branch on merge and that would close them. To read the gate's verdict without merging or labelling, run `tools/merge-pr.sh --check <n>`: it runs the same checks as the merge, prints each check's state (its newest non-skipped run), and exits 1 with the `REFUSED:` line when the merge would refuse. Exit 0 means nothing blocks the merge except what the last line lists (`GATE OK except: draft, no review pass`). A draft and a missing `review-passed` pass are notes, not refusals. It runs `git fetch origin main`, which updates only the local `origin/main` ref. Reviewers judge CI and the body and label rules from this, never from `gh pr checks` or `statusCheckRollup`: a later skipped run hides an earlier failed one there (PR 397 passed review with a red client suite). To merge two or more review-passed PRs, use the batch tool: `tools/merge-batch.sh <n>...` (below). To merge them one at a time, with GitHub's merged state, use the queue instead of a hand-rolled waiter: `tools/merge-queue.sh <n>...`.

- It merges the PRs one at a time, in the order given. For each it waits until no workflow run for the head is unfinished, then runs the gate.
- On a stale-base refusal (the `REFUSED:` line carries the marker `[stale-base]`, which the queue matches; a run from before CI recorded its main counts) it re-runs whole (`POST actions/runs/<id>/rerun`, once per distinct run) the runs holding the head sha's newest non-skipped `build`, `tool-tests` and (when one ran) `client-gametest` jobs (`build` and `client-gametest` are aggregates: each shares its run, `CI` or `Client tests`, with its shards), found by listing each run's jobs (a run can be non-skipped with a skipped `client-gametest` job, #1092; never a single job: a job re-run copies the run's other finished jobs without their `merged-main` annotation, so the gate calls the base stale again, #1094; each job merges the live `origin/main`, so the recorded sha refreshes), waits for CI again and retries (`MERGE_QUEUE_STALE_RETRIES`, default 3). A run still in progress is skipped, not cancelled: the queue's wait covers it, and if it finishes stale the next retry re-runs it. No such job for the sha, or a re-run the API refuses (a run older than 30 days), stops the queue with the reason. It never changes a PR's state: closing and reopening a PR to kick CI is forbidden, and `tools/tests/no-pr-reopen.test.sh` fails any tool that PATCHes a PR's `state`. On `mergeable: UNKNOWN` it waits 30 s and retries (4 times).
- On a client-only refusal (the `REFUSED:` line carries `[client-only]`: every check that is not passing is a failed, timed-out or cancelled `client-gametest` or `client-gametest-shard <i>` job, and `build` and `tool-tests` passed) it re-runs whole the `Client tests` run holding the head's newest non-skipped `client-gametest` job (the same mechanics as the stale-base re-run, never `--failed` or one job; why in the client-suite note below), waits for CI again and retries (`MERGE_QUEUE_CLIENT_RETRIES`, default 1). A second client failure stops the queue with the gate's reason. A failed `build` or `tool-tests`, alone or beside a client failure, is never re-run.
- A PR that is already merged is skipped. Any other refusal stops the queue and prints the reason.
- After each merge, cleanup never loses work. It removes the PR's worktree with a plain `git worktree remove` (no `--force`), and only when that worktree is under `<primary checkout>/.claude/worktrees/`, has no uncommitted changes, and is not the one running the queue. Otherwise it prints `left: <path> (<why>)` and moves on. It finds the worktree by its branch (the PR's head branch), else by a `HEAD` equal to the PR's head sha (a `worktree-agent-<id>` branch, which is then the branch it deletes; a detached HEAD deletes none). It deletes the local branch only when its tip is the PR's head sha or is on `origin/main`. It then runs `git pull --ff-only` in the primary checkout, only when that is on `main` and clean; it never rebases or autostashes.
- It prints each step as it happens and ends with a summary (merged, skipped, stopped and why, not attempted). Exit status is 0 unless it stopped.
- Only one queue runs at a time (a symlink lock, `~/.cache/deepcharter/merge-queue.lock`, whose target is the owner's PID). A second one exits with status 3 and does not wait. A lock whose owner is dead is taken over; an unreadable one counts as held.

## Batches

[ADR 0106](../../../docs/adr/0106-reviewed-prs-merge-in-batches-on-an-integration-branch-with-one-ci-run.md), amended by [ADR 0113](../../../docs/adr/0113-single-prs-merge-as-a-batch-of-one-and-the-roadmap-rides-in-the-landing.md). `tools/merge-batch.sh <n>...` for one or more PRs (`tools/merge-pr.sh <n>` is a batch of one); it never resolves a conflict.

- **Preflight.** Each PR runs `tools/merge-pr.sh --preflight <n>`: the gate without CI and mergeability (open, not a draft, `review-passed` at the head, closes its branch's issue, body and labels, targets `main`). A PR that fails is listed under `refused` and left out.
- **Build.** `batch/<utc-stamp>` off `origin/main`; each PR, in the order given, is squashed (`git merge --squash`) as one commit `<title> (#n)` with `Closes #<issue>` and the trailers (`MERGE_BATCH_TRAILERS`). A PR that conflicts with `main` or an earlier PR in the batch, adds nothing, adds an ADR number already on the batch, or whose head is not the one its preflight judged (the preflight prints it; checked on every build, rebuilds included) is **dropped** and listed under `dropped` with the reason; the batch goes on without it. A dropped PR is not closed or changed: fix its conflict, re-mark it, and put it in the next batch.
- **Chains.** A PR whose head has another listed PR's head (a preflight-refused one too) as a proper ancestor, because its branch merged that PR's branch, is chained to the nearest such PR (the one no other ancestor descends from). The batch lists predecessors first, whatever order they were given in. A chained PR is squashed with a three-way merge whose base is the predecessor's head (`git merge-tree --write-tree --merge-base=<prev head> <batch> <head>`), so only its own increment lands: one commit per PR, as above. A chained PR whose predecessor is neither on `main` (a commit ending `(#n)`, or the PR merged) nor landed in this batch is **dropped** (`chained to #N, which did not land`), also when it falls back to `tools/merge-pr.sh`; so is a chained PR that conflicts, and every later link. A chained PR must still target `main` (retarget stacked PRs first). A red split keeps the chains: a prefix of a chain is valid alone, and the second half builds its first link on the prefix already on `main`.
- **CI.** One PR into `main`, labelled `gameplay` (the full client suite runs) and `no-demo`, with `No demo:` and `No map change:` body lines. `tools/merge-pr.sh --ci <batch pr>` reads the verdict (check runs, required checks, stale base, client suite). A `[client-only]` failure re-runs the whole `Client tests` run once (`MERGE_BATCH_CLIENT_RETRIES`). A `[stale-base]` verdict, or a landing push that is rejected as non-fast-forward (`main` moved), or `origin/main` having moved by anything but a generated file (below) since the batch's base, rebuilds the batch on the new `main` and runs CI again (`MERGE_BATCH_STALE_RETRIES`, default 3); then the tool stops and reports. Any other push failure stops the tool at once.
- **Generated files.** `tools/lib/generated-paths.sh` lists the files the merge tools generate and commit to `main` (`docs/ROADMAP.md`, `.papercuts.jsonl`). A `main` that moved since the batch's base only by those is not stale: the batch's commits are cherry-picked onto it (a conflict, or a replayed tree that differs from the verified one by anything else, rebuilds the batch) and CI does not run again. The stale-base rule of the gate reads the same list.
- **Roadmap.** The landing carries the roadmap: one commit `Regenerate roadmap after batch #<n>` on top of the verified head, rendered as it reads once the batch has landed (`tools/roadmap.py --landing <pr>:<issue> --hide <batch pr>`), pushed with the batch. No roadmap commit follows. A roadmap that cannot be generated is a warning and the batch lands without it. `merge-pr.sh --direct` (the queue) still regenerates it in a commit after the merge.
- **Merge.** The repo allows squash merges only, so the CI-verified batch head is pushed to `main` with a plain fast-forward push (never forced), only while `origin/main` is still the batch's base (or has moved only by generated files): `main` gets one commit per PR. The batch PR is closed with a comment naming the sha. Each original PR gets the comment `Merged in batch #<n>`, is closed, has the PRs stacked on its branch retargeted to `main`, and loses its branch; the batch branch is deleted. The originals and the batch PR show as closed, not merged: **use the queue when a PR must show GitHub's "merged" state.** A PR whose squash is empty because `main` already holds its `(#n)` commit (a rerun after a killed run) is closed as merged instead of dropped.
- **Red.** The batch PR is closed and the PRs split into two halves, each a new batch; a batch of one PR (also one a build shrinks to) that is red is refused with the CI reason and left open. Another failure of the gate (no checks, an unreadable run) stops the tool instead.
- Exit status is 0 only when every PR merged; the summary lists merged, dropped, refused and stopped PRs.

## GitHub and CI gotchas

- The merge proxy refuses (HTTP 403) a commit title or message with a URL of 150+ characters after `://` or an 80-character run after `?`, `/`, `=` or `#`. `merge-pr.sh` sends the title and body through `tools/merge_message.py`, which turns a long blob URL into its backticked path and drops other long URLs (keeping link text); the PR body is not edited, and `--check` warns when a rewrite will happen (#1007). A failed merge request prints the API's error text.
- The gate reads the closing set from the PR body with `tools/closing_refs.py` (grammar in its docstring; `tools/roadmap.py` uses it too). The closing set is exactly the branch's issue (`<issue>-<slug>`): mention any other issue in prose, never after a closing keyword, and close it by hand after the merge. Prose such as "the same fix #252 verified" counts as a reference too, so phrase it another way. A link made by hand in the sidebar is not seen.
- `tools/mark-review-passed.sh` refuses when GitHub's head sha differs from `git ls-remote origin <branch>` (right after a push it can lag): wait and retry.
- The gate blocks on any failing check on the head sha, not only `REQUIRED_CHECKS`.
- A check-run, `merged-main` annotation or changed-files listing that cannot be read in full refuses with gh's error, after `gh_list` retries a transient failure (why and which: `tools/lib/gh-rest.sh`, #1484).
- The gate refuses a PR whose changed paths make `tools/ci-client-needed.sh` print `true` unless `client-gametest` has a non-skipped passing run on the head sha. It applies to PRs already open: a game-code PR whose client run was skipped is refused until it gets a real run.
- The server suite runs as four parallel `build-shard <i>` jobs (`-PgametestShard=i/4`, split by weight with each campaign environment kept in one shard, #1327, [ADR 0106](../../../docs/adr/0111-the-server-gametest-suite-runs-as-four-weighted-shards-under-one-build-check.md)) beside `build-checks` (`./gradlew build -x runGameTest`, `gate_checks.py`, the client run tasks' dry run), and `build`, the required check, is their aggregate: it passes only when all of them did and their merged mains agree, and then records that main in its own `merged-main` notice (`tools/ci-shard-main.sh` from main, `SHARD_KIND=build`). The gate reads that notice and each passing shard's and `build-checks`'s. Once any `build-shard` or `build-checks` run exists for the head, it refuses unless `build-checks` and at least one shard passed and no shard was only skipped; a head with none (CI from before #1327) is read from its single `build` job's notice. A never-started `build-shard ${{ matrix.shard }}` template run is dropped like the client one.
- The client suite runs as parallel `client-gametest-shard <i>` jobs (matrix in `client-tests.yml`, split by weight, #1079) and a `client-gametest` aggregate that passes only when every shard did. The gate treats a failed shard like any failed check and requires the aggregate on a game-code PR, and refuses an aggregate pass with no passing shard. The aggregate also records the shards' agreed `merged-main` notice (`tools/ci-shard-main.sh`) for the gate on main (#1093); this gate reads the shards' notices, never the aggregate's. Temporary exception (#1116): when no `client-gametest-shard` run exists at all (CI from before sharding), a `client-gametest` pass is accepted only if that job itself recorded `merged-main`. Each shard merges the live main when it runs, so a `--failed` re-run re-merges main in only the shards it re-runs: once main has moved, the aggregate fails ("The client shards merged different mains", #1451). The queue re-runs the whole run itself on `[client-only]`; by hand, re-run the whole run (`gh run rerun <run id>`, or `POST actions/runs/<id>/rerun`), never `--failed` once main has moved.
- `client-gametest` shows "skipping" for runs from a non-`gameplay` label event (every stage-label change): run `tools/merge-pr.sh --check <n>` before believing the client suite was skipped (it reads the newest non-skipped run; the client job is not in its required list, but a failing one is shown and refuses).
- A PR pushed while draft can end with only skipped CI on its head even after `gh pr ready`, and a conflicting PR gets none: check `gh run list --branch <b>`, then re-run the whole runs holding its newest non-skipped `build`, `tool-tests` and `client-gametest-shard` jobs (the `build` shards share the `build` run) (`gh run rerun <run id>`, never `--job`: see above; a label event adds skipped runs on top), or push a commit if the PR conflicts (a conflicting PR gets no run). After a local conflict resolution a PR head can stay stale and conflicting: push again, then re-mark the pass.
- CI merges the PR head with `origin/main` fetched at run time (`.github/actions/merge-main`, never `refs/pull/N/merge`) and records that sha in a `merged-main` annotation on each job's check run. The gate refuses with `[stale-base]` unless the newest `build`, `build-shard`, `build-checks`, `tool-tests` and `client-gametest-shard` runs (or, until #1116, the legacy single `client-gametest` job when no shard run exists) recorded the current `origin/main` (only a difference in generated files, `tools/lib/generated-paths.sh`, is tolerated); `--check` prints each recorded sha (#979). A client-suite failure on a queue re-run whose merge commit passed before (#584) is the `[client-only]` case above: the queue re-runs the whole `Client tests` run once.
- A whole rerun of `Client tests` re-decides `client-changes` from `git diff <live main> HEAD`: if main moved so the PR no longer trips `tools/ci-client-needed.sh`, the client shards are skipped on the rerun, the gate falls back to the older run's stale `merged-main`, and the queue stops with "still stale after 3 reruns" (fails closed). Remedy: push a commit, or merge main into the branch.
- CI runs main's copy of `merge-main` and `tools/ci-merge-main.sh` (`@main`), so a PR that changes either is first exercised by the next PR. Test such a change with `tools/tests/ci-merge-main.test.sh` plus a follow-up PR; `tools/tests/ci-merge-main-uses.test.sh` keeps the jobs that merge main (the `build` shards, `build-checks`, `tool-tests`, `client-changes` and each `client-gametest-shard`) on the remote ref (#983). The aggregates (`build`, `client-gametest`) never merge main: they run main's `tools/ci-shard-main.sh` from a `.ci-main` checkout.
- `merge-queue.sh` reports "state: unknown" if `gh` goes missing after a merge: check the state with `gh api repos/pkeppeler/deepcharter/pulls/<n> --jq '[.merged, .state]'` before re-queuing. A papercut written in the main checkout blocks the queue's main update: hand the line to an in-flight PR and restore the file.
- Adding and removing the same label in one call removes it (`gh pr edit` did; with REST, `POST issues/<n>/labels` adds and `DELETE issues/<n>/labels/X` removes, so call them in order). `jq` is not installed: use `gh --jq` or `tools/py`. `pull_requests[].base.sha` on a run is live, not the base at run time.
- A change to a `--jq` filter in the merge tools is tested on recorded JSON: the shell tests' `gh` stubs run the script's own filter over `tools/tests/fixtures/gh-rest/` (`STUB_FIXTURE_PR`, `STUB_FIXTURE_COMMENTS`, `$ST/fixture.N`) through `tools/tests/lib/gh-fixture.sh`, which needs `jq`. Without it those cases print `SKIP`; CI has it. A fixture edited by hand has `hand-edited` in its name ([README](../../../tools/tests/fixtures/gh-rest/README.md)).

# Merging

Merge only through `tools/merge-pr.sh <n>`, which refuses and gives the reason. It retargets open PRs stacked on the PR's branch to its base first, because GitHub deletes the head branch on merge and that would close them. To read the gate's verdict without merging or labelling, run `tools/merge-pr.sh --check <n>`: it runs the same checks as the merge, prints each check's state (its newest non-skipped run), and exits 1 with the `REFUSED:` line when the merge would refuse. Exit 0 means nothing blocks the merge except what the last line lists (`GATE OK except: draft, no review pass`). A draft and a missing `review-passed` pass are notes, not refusals. It runs `git fetch origin main`, which updates only the local `origin/main` ref. Reviewers judge CI and the body and label rules from this, never from `gh pr checks` or `statusCheckRollup`: a later skipped run hides an earlier failed one there (PR 397 passed review with a red client suite). To merge several review-passed PRs, use the queue instead of a hand-rolled waiter: `tools/merge-queue.sh <n>...`.

- It merges the PRs one at a time, in the order given. For each it waits until no workflow run for the head is unfinished, then runs the gate.
- On a stale-base refusal (the `REFUSED:` line carries the marker `[stale-base]`, which the queue matches) it closes and reopens the PR (`PATCH pulls/<n>` with `state=closed`, then `state=open`), waits for CI again and retries (3 times). On `mergeable: UNKNOWN` it waits 30 s and retries (4 times).
- A PR that is already merged is skipped. Any other refusal stops the queue and prints the reason.
- After each merge, cleanup never loses work. It removes the PR's worktree with a plain `git worktree remove` (no `--force`), and only when that worktree is under `<primary checkout>/.claude/worktrees/`, has no uncommitted changes, and is not the one running the queue. Otherwise it prints `left: <path> (<why>)` and moves on. It finds the worktree by its branch (the PR's head branch), else by a `HEAD` equal to the PR's head sha (a `worktree-agent-<id>` branch, which is then the branch it deletes; a detached HEAD deletes none). It deletes the local branch only when its tip is the PR's head sha or is on `origin/main`. It then runs `git pull --ff-only` in the primary checkout, only when that is on `main` and clean; it never rebases or autostashes.
- It prints each step as it happens and ends with a summary (merged, skipped, stopped and why, not attempted). Exit status is 0 unless it stopped.
- Only one queue runs at a time (a symlink lock, `~/.cache/deepcharter/merge-queue.lock`, whose target is the owner's PID). A second one exits with status 3 and does not wait. A lock whose owner is dead is taken over; an unreadable one counts as held.

## GitHub and CI gotchas

- The gate reads the closing set from the PR body with `tools/closing_refs.py` (grammar in its docstring; `tools/roadmap.py` uses it too). Only the first reference after a keyword counts, so write `Closes #1` and `Closes #2` as two keywords; prose such as "the same fix #252 verified" counts too, so phrase it another way. A link made by hand in the sidebar is not seen.
- `tools/mark-review-passed.sh` refuses when GitHub's head sha differs from `git ls-remote origin <branch>` (right after a close/reopen it can lag the push): wait, or close and reopen.
- The gate blocks on any failing check on the head sha, not only `REQUIRED_CHECKS`.
- `client-gametest` shows "skipping" for runs from a non-`gameplay` label event (every stage-label change): run `tools/merge-pr.sh --check <n>` before believing the client suite was skipped (it reads the newest non-skipped run; the client job is not in its required list, but a failing one is shown and refuses).
- A PR pushed while draft can end with only skipped CI on its head even after `gh pr ready`, and a conflicting PR gets none: check `gh run list --branch <b>`, then close and reopen it (`gh api -X PATCH repos/pkeppeler/deepcharter/pulls/<n> -f state=closed`, then `-f state=open`). After a local conflict resolution a PR head can stay stale and conflicting; close and reopen to sync, then re-mark the pass.
- After a base PR merges, a dependent PR's re-run can check out GitHub's stale `refs/pull/N/merge`: see `HEAD is now at` in `gh run view <id> --log`, and close and reopen once `gh api repos/pkeppeler/deepcharter/pulls/N --jq .merge_commit_sha` is fresh. A client-suite failure on a queue re-run whose merge commit passed before gets one `gh run rerun <id> --failed`, then a re-queue (#584).
- `merge-queue.sh` reports "state: unknown" if `gh` goes missing after a merge: check the state with `gh api repos/pkeppeler/deepcharter/pulls/<n> --jq '[.merged, .state]'` before re-queuing. A papercut written in the main checkout blocks the queue's main update: hand the line to an in-flight PR and restore the file.
- Adding and removing the same label in one call removes it (`gh pr edit` did; with REST, `POST issues/<n>/labels` adds and `DELETE issues/<n>/labels/X` removes, so call them in order). `jq` is not installed: use `gh --jq` or `tools/py`. `pull_requests[].base.sha` on a run is live, not the base at run time.
- A change to a `--jq` filter in the merge tools is tested on recorded JSON: the shell tests' `gh` stubs run the script's own filter over `tools/tests/fixtures/gh-rest/` (`STUB_FIXTURE_PR`, `STUB_FIXTURE_COMMENTS`, `$ST/fixture.N`) through `tools/tests/lib/gh-fixture.sh`, which needs `jq`. Without it those cases print `SKIP`; CI has it. A fixture edited by hand has `hand-edited` in its name ([README](../../../tools/tests/fixtures/gh-rest/README.md)).
